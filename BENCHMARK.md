# Ladybird against Ardia and Helium

A reduced, Linux port of the benchmark in [Ardia's `vs-browsers.md`](https://github.com/ardia-browser/ardia/blob/main/docs/perf/vs-browsers.md), comparing the locally installed Ladybird 2026.47.7, Ardia 0.2.48 and Helium 0.22.2.1.

**Why Ardia appears as Chrome here:** the Linux Ardia build is a Chromium 158 fork. Its CDP endpoint reports `Browser: Chrome/158.0.8127.36`, and `ardia --version` prints `Chromium 158.0.8127.36`. That is the browser's Chromium identity, not a different product; the launcher is `/usr/bin/ardia` → `/usr/lib/ardia/ardia-launch`. The macOS-specific rendering work behind Ardia's published results is not part of this Linux build, so these numbers do not test that work.

**This is not the same harness and the numbers are not comparable with Ardia's published table.** Different OS, hardware, rendering mode and workload. Only the three-browser comparison on this machine is meaningful.

**Read the row labels before the numbers.** The three browsers cannot be instrumented identically. Rows that mix instrumentation are labelled and are not ranked; only comparable rows are bolded.

Usage, requirements and the file map are in [README.md](README.md). Run commands are in [README.md#run](README.md#run).

## Method

- **Machine.** Linux x86_64 (CachyOS, kernel 7.3.5-2-cachyos-bore-lto), Wayland session. The owner's other apps (mpv, koe, Cressida and an interactive Ladybird instance) stayed open. Neither browser under test had exclusive use of the machine, and no caches were purged.
- **Headless.** Ladybird `--headless=manual`; Ardia and Helium `--headless=new`. The current harness defaults to `--disable-gpu` for both Chromium browsers and records the setting; set `GPU=1` to enable the GPU for both. The saved runs do not record which flag was used, which is a provenance gap in the older data.
- **Fresh state.** Every launch used a new profile: `--temporary-profile` / `--profile-path` for Ladybird, `--user-data-dir` for Ardia and Helium. Profile directories are removed after Chromium runs.
- **Workload.** A single small local HTML page served from `127.0.0.1`, with a coloured block and a short script. It is much lighter than the real sites in Ardia's run, so absolute times are not comparable to theirs.
- **Timing.** The clock starts before `Popen` is called for spawn→paint. The comparable request→paint clock starts on the harness server when the page request arrives and stops when the paint signal reaches the harness. Ladybird paints arrive through a page beacon using `PerformanceObserver`. Ardia and Helium paints arrive through CDP `Page.lifecycleEvent` (`firstContentfulPaint`), timestamped when the harness receives them.
- **Memory and CPU.** Pages are opened with `window.open()` in one instance and sampled after all requested tabs have loaded, over the `SAMPLE_S` idle window (6 s by default in the saved run, 8 s for the unused `bench.py` steady path). Memory is PSS/RSS summed over the process tree. PSS is not macOS `phys_footprint`. CPU is the `utime+stime` delta as a percentage of one core. GPU processes and extension processes are excluded from CPU identically for every browser, and the excluded CPU is written to the result file. Memory includes every process in the current harness; see the saved-run caveat above.
- **Incomplete runs.** A tab run that opens fewer tabs than requested is written with `complete: false` and left out of medians instead of being averaged in silently.
- **Interleaving and rotation.** Cold-launch rounds rotate the browser order. Tab runs rotate by round and tab count. Nothing is pooled across invocations except within one result file, and the primary and replication runs are reported separately.
- **Instrumentation.** Every result file written from now on contains a `meta` block with UTC start time, git commit and dirty state, OS and kernel, Python version, load average, browser paths and version strings, the exact argv, and every setting used. The saved files above predate this and are marked as such.

## Changes from the earlier table

The earlier version mixed new-tab methods, quoted a Helium `n=9` new-tab sample that no saved file contains, dropped Ladybird's lowest samples while keeping Helium's high outlier, and reported one of three memory runs. It also timed launch after `Popen`, sampled only the root PID for steady state, and bolded overlapping ranges. The generated tables now keep all saved samples and runs, show source files, and rank only disjoint ranges. Obsolete numbers are not reproduced.

## Limitations

- The saved memory and CPU data is two samples per cell. Treat it as indicative, not publication-grade.
- The saved files predate the metadata, request→paint, load-beacon and complete-run changes, so those fields are absent from the tables until the harnesses are rerun. The saved popup new-tab values are also aggregated across runs, so they cannot be tied back to individual complete runs.
- Ardia's CPU is not comparable because of the headless `chrome://ardia` spin. Its memory is reported, but the saved run excluded extension processes from PSS, which may make Ardia's memory slightly low relative to a whole-tree measurement.
- Headless-only: no GUI, window, session-restore or wakeup rows; tab switch is CDP-emulated in the Ardia-shaped table.
- The browsers use different paint instrumentation (page beacon vs CDP), and the saved launch row still carries CDP setup overhead for Ardia and Helium. The request→paint row is the designed remedy, but it is not present in the saved data.
- Ardia's Linux build is Chromium 158 with the Ardia shell. The macOS-specific compositor and wakeup work measured in Ardia's published table is absent here.
- Ardia's own table does not claim an overall win: Chrome leads most of its rows. This table should not be presented as contradicting or confirming that claim.
- Full Ardia-equivalent coverage would require a macOS harness driving real windows via CDP plus Mach wakeup and footprint counters.
